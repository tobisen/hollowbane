# Risk-based release policy (DBL-010)

This policy supersedes the former requirement to run every browser scenario on every push. No gameplay changes are included. The last Full release baseline is `80185a6183370995869348f95a754027715a1c11`: 20m23s including Pages and hosted acceptance (second successful sample20m37s). The2–5minute Fast target is unverified until measured on GitHub.

| Tier | Trigger                                                                                                                       | Required coverage                                                                                                                                                                                                                                                                                           |
| ---- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fast | Ordinary main pushes and PRs                                                                                                  | Full TypeScript/lint/format;29 core deterministic unit contracts (including six policy cases); nine Python artifact/gate checks; one production build; two Chromium cases for application/SHA and real controller boss damage; affected unit/integration groups                                             |
| Full | Manual `Full Regression`, release workflow `tier: full`, `v*` tags, broad contracts, uncertain impact or policy/build changes | All482 units (473 original+two shard+six policy+one navigation driver); all143 existing Chromium scenarios in two shards; existing15 Chromium/Firefox/WebKit compatibility cases; all persistence/migration, visual and campaign cases in those collections; original validators and tooling/dry-run checks |
| Deep | Manual `Deep QA`                                                                                                              | Full plus existing broader Firefox/WebKit regression,64 seeds across two outdoor areas with deterministic replay/connectivity, three50000-item loot reports with replay/validity/distribution assertions, software-rendered performance measurements                                                        |

Full and Deep are independent manual workflows; Full is also reusable and becomes a required predecessor of Pages when the release plan selects it. A standalone manual run does not publish. Deep does not authorize ordinary release and has no automatic trigger. Full is mandatory before major milestone approval even if its individual increments passed Fast. Existing campaigns remain in Full; there is no new D08-B campaign conclusion to accept. Deep cannot certify physical hardware.

## Selection and conservative fallback

`scripts/ci-policy.mjs` emits an inspectable `ci-plan.json`, retained as the release-plan artifact and shown in the Actions summary. The executable group mapping and complete retained file inventory are in `docs/ci/test-inventory.json`. All original tests remain directly runnable with their original npm commands/configurations.

The planner combines an explicit domain mapping, parsed TypeScript imports/re-exports/dynamic literal imports, reverse transitive dependencies and changed diff content. Matching files alone do not decide the gate. It selects dependent unit files and all mapped domain unit files; more than35 impacted unit files forces Full. Changed public/data contract lines, deletion, unknown runtime inputs, build/dependency/tooling/workflow changes and unavailable history force Full. A caller can request Full but cannot force Fast. Unknown/unmapped modules, including shared combat/input foundations, require Full.

Main compares the current commit against the last successful main Verify-and-deploy workflow SHA from the read-only Actions API, after proving it is an ancestor. It also reads that run’s jobs and requires successful verify, Pages and hosted jobs: a historic green workflow with skipped publication is not an accepted baseline. This includes changes from an earlier failed/cancelled push or a Pages deployment whose hosted gate failed, preventing a later prose-only push from bypassing them. Missing/invalid/network-unavailable accepted history means Full. PRs compare against their base SHA. Mixed affected groups run all selected integrations before deployment; the hosted suite chooses the current critical flow in quest→persistence→world→boss order. Campaign changes run application/SHA plus three focused finale cases (fight/reload, safe return, and controller conclusion/reward reload); other groups retain two cases including application/SHA. Full still includes every controller and boss case.

## Artifact and release gate

Fast builds once, seals full SHA and file hashes, and tests that artifact. Required Full shards/compatibility download and verify exactly those bytes. The existing `verify` check always runs and rejects a failed, cancelled or skipped Fast; it accepts skipped Full only when the plan explicitly selected Fast. Required Full must succeed. Pages depends on verify; hosted verification depends on successful Pages. Deploy and hosted jobs use explicit cancellation/success guards so a correctly skipped optional Full cannot skip them through transitive GitHub job dependencies. An always-run final Release acceptance job rejects skipped/failed Pages or hosted jobs on main; the workflow succeeds only after hosted manifest/SHA/every application byte and all selected browser cases pass. PRs and tags run their required verification without publishing. Do not start another deliverable while required CI, Pages or hosted acceptance is pending/failed.

Only deploy has Pages write/OIDC permissions. Fast has contents/actions read to identify the last fully accepted release; other jobs have contents read. Existing npm lock/install, Ubuntu24.04, browser versions, screenshots and assertion timeouts remain. No dependency/browser environment/snapshot/gameplay changes. Passing jobs upload JSON only; failing jobs retain screenshots/traces. The old executable pipeline remains available as manual `Previous full release (manual rollback)`; its exact original source is archived in `verify-deploy.before.yml`. Never dispatch it concurrently with a release under verification.

Branch main currently has no GitHub branch protection (API404); this task does not change repository settings. The workflow enforces its own deploy dependencies and preserves the `verify` check identity. Conditional Full has no independent required status configured; skipped suites cannot leave verify pending. Long reusable Full jobs use `!cancelled()` guards so cancellation can stop expensive obsolete runs; only the short final aggregate uses `always()`. Major milestone tagging/manual Full remains a maintainer responsibility because commit content cannot infer product milestone approval.

## Slow tests and validation

The final baseline Chromium shards took908s and638s; npm install took3–5s and the build8.34s. The full campaign/kill/save scenario takes about69s and carries genuine input→combat→XP→loot→atomic reload assertions. It remains unchanged in Full. Full gamepad/menu and projected-input driver fixes from the prior release remain intact. Fast reuses the existing isolated controller encounter instead of repeatedly navigating a long campaign. No assertions, precision, timeouts, snapshots or retries were changed.

Local focused validation:29 selected units, eight artifact/gate Python cases, strict TypeScript/lint/build, workflow trigger/permission/dependency validation,143-case exact shard coverage, seven additive Deep corpus checks, and two real Fast browser cases. A deliberately wrong deployed SHA must fail the actual artifact smoke; its failed result must reject the same risk gate used before Pages. Policy tests exercise save integration, transitive dependencies, shared/public contracts, unknown/deleted inputs and Full overrides. GitHub must then run Full once for this policy change, verify exact Pages/hosted, followed by an ordinary Fast-only evidence increment. Timings and exact SHAs will be recorded in `measurements.md`; no speed improvement is claimed before those runs complete.
