# Required release tiers (DBL-010)

The current release gate is automatic **Fast / Integration / Full**, followed by exact-SHA Pages publication and hosted smoke. [Measured October23 repair and verification](2026-10-23-ci-improvement.md) supersedes the older two-tier measurements. Targets are2–5 minutes for ordinary releases and5–10 minutes for medium risk where feasible; measured results and limitations belong in that record. Full remains mandatory for milestones and broad/unknown changes. Deep QA remains manual and preserves its broader compatibility/generation/loot/performance corpus.

## Coverage and classification

Every tier runs static checks, release-artifact/gate tooling, critical contract units, a single sealed production build and two real Chromium smoke cases: exact-SHA application load and virtual-controller lock/assigned-skill damage. Fast additionally runs directly affected units. Integration adds mapped domain units and reverse-import consumers, then every affected browser file across up to two separate single-worker runners. Full runs every unit/validator/tooling check, every existing Chromium scenario across four separate single-worker runners and all15 required Chromium/Firefox/WebKit inventory contracts. [Executable groups and complete retained inventory](test-inventory.json) and [whole-file timing weights](browser-durations.json) are inspectable. Whole files preserve serial campaign handoffs and hooks; original assertions, precision, snapshots and deadlines remain. No tests were deleted or made optional to hide failures.

The planner in `scripts/ci-policy.mjs` combines real before/after source, parsed public TypeScript contracts, domain mappings and reverse transitive imports. Any changed public signature/type, save/migration/schema/serialization/version content, deleted or unclassified runtime input, shared combat/input foundation, build/dependency/tooling/workflow edit, or more than35 affected unit files or more than three domain groups requires Full. Invalid/missing source or release history fails closed. Explicitly typed implementation changes with stable contracts can select Integration; a line containing `export` alone is insufficient to call an implementation an API break. Inferred return changes and internal type declarations remain conservative. A caller may request Full, never a lower tier.

Changes to known browser specs select the whole file. Changes to test fixtures/helpers select **every** transitive browser and unit consumer; an unmapped helper requires Full. The D14 release acceptance milestone remains Full. Tags and explicit manual Full remain milestone gates; automatic classification cannot infer product milestone approval.

Main compares against the last successful main Verify-and-deploy run only after its verify, Pages and hosted jobs are proven successful and its SHA is an ancestor. This preserves all changes from earlier failed/cancelled/unaccepted pushes. No trustworthy baseline means Full. An empty diff is trusted only when HEAD equals the accepted SHA. PRs compare against their base. Each plan is retained as `release-plan/ci-plan.json` and summarized in Actions.

## Execution and publication

Fast builds and seals once. Integration or Full jobs download and verify those exact bytes. Full covers affected behavior once, instead of following an initial copy of all affected browser cases. Runner isolation, one browser worker and refreshed duration weights limit software-renderer contention. npm cache remains. Browser binaries are cached by locked dependencies/browser family; required libraries and fonts still install through the primary HTTPS Ubuntu mirror. There is no browser/dependency version change. Normal push/PR triggers and cancellation of obsolete same-ref runs remain; no extra release workflow is launched automatically.

The always-running `verify` aggregate preserves its check identity and rejects failed/cancelled/skipped required jobs. Integration must succeed for that tier; Full must succeed for Full. A failed optional job is also rejected. Pages depends on `verify`. Hosted checks verify the full SHA and every sealed application byte, then run the same two stable real gameplay smoke cases on Pages. A final always-running Release acceptance rejects missing/failed verify, Pages or hosted jobs on main. PRs/tags do not publish. Only deploy has Pages/OIDC write permission. Exact commit and publication guarantees are unchanged.

## Reproducible affected-gameplay measurement

The optional manual `integration-probe=inventory-ui` adds the recorded inventory modal/focus implementation change at a615c2a's `src/rendering/inventory-view.ts`. It reads the real before/after diff from ancestor-checked history and merges its required units/browser files with actual release risk. It can only add coverage: actual Full remains Full. After the CI change's mandatory Full release passes, the same accepted SHA can be released through this Integration replay without changing gameplay. The report must call it a replay, distinguish it from a new gameplay feature, and record actual durations, suites and SHA. Unknown probe values fail. No arbitrary “fast” label, comparison base or path exclusion is accepted.

Before activating policy changes, run focused policy/import/public-contract and shard checks, strict static checks, the Python gate/artifact suite, exact complete browser inventory coverage and a deliberately failing real browser SHA test through the deployment gate. Then require one Full GitHub/Pages/hosted release. Document actual measured release behavior; do not claim physical-controller or reference-hardware evidence from browser tests.
